# Research proposal review, 2026-10-21

The supplied 50-page PDF combines working notes from several research sessions. Most repo evidence describes 1.18.0; one partial section still describes an older version. The notes explicitly identify uncertain claims and unmeasured performance inferences. Decisions below compare those proposals with the current 1.19.2 local code rather than treating the document as an implementation specification.

## Implemented in local 1.19.3

- **Bound CSV imports.** The reported whole-file unbounded read was still present. File bytes, decoded characters, row count, columns and individual fields now have limits, including pasted CSV. Oversized input fails before replacing the current queue. Canonical download-index parsing is not subject to import row limits.
- **Framework/TLS correctness.** The raw compiler build had no TargetFrameworkAttribute and four app paths forced TLS 1.2. The assembly now explicitly targets .NET Framework 4.8 and the app leaves protocol negotiation to Windows. This follows [Microsoft's .NET Framework TLS guidance](https://learn.microsoft.com/en-us/dotnet/framework/network-programming/tls). PowerShell setup behavior, certificate verification and search pacing are unchanged. Public HTTPS album imports were checked after the change.
- **Local diagnostics export.** Added Save diagnostics to the existing preview. It saves only the same generated allowlisted report, atomically, with no automatic upload or raw-log export.

## Already covered or contradicted by newer code

Album-folder discovery, missing-track-only album downloads, flat music folders, album numbering, completion cleanup, full decode through a supplied FLAC tool, artwork, paced retries, source details, CSV drag/drop, private credential handling, bounded Activity display and pinned build dependencies already exist. The new storage checks in local 1.19.2 also cover the app drive as well as the music drive. Do not reintroduce nested templates or cover sidecar clutter into the default music layout.

## Deferred with reasons

- **Sockseek update:** validate the exact upstream release, source, hashes and progress schema, then run an isolated live transfer compatibility check before replacing the pin. The PDF itself lacks this evidence. No engine is swapped solely because a newer version exists.
- **Persistent engine/daemon and stdout-worker redesign:** changes process lifetime, index ownership, cancellation and crash recovery. It needs measured bottlenecks and interruption tests before becoming a reliability improvement. No search-rate increases are justified by these notes.
- **Persistent logs and restart-triggered downloads:** logs can contain private tracklists/peers/paths, and silently starting downloads on launch changes an established behavior. Keep explicit starts and allowlisted diagnostics for this update.
- **Settings recovery:** the reported fallback-on-read-error merits a separate change with explicit recovery behavior and tests proving damaged/locked settings are never overwritten. It is not bundled into the runtime/import work.
- **Signing, attestations, release automation, updater and package-manager distribution:** worthwhile separate release work, with signing-provider eligibility, state migration and artifact trust validated first. No account enrollment, permission expansion, publication or uploads are implied by reviewing the PDF.
- **DPI overhaul, controller extraction, SDK/backend migration:** retain working behavior until there is a concrete acceptance test and measured benefit. No speculative UI rewrite or dependency migration.
- **Fingerprint identification, ReplayGain, lyrics, tag rewriting and spectral verdicts:** introduce services, tools, licensing or metadata risks. Existing decode checks verify integrity, not lossless provenance. Do not add an unreliable quality verdict or rewrite tags from uncertain matches.

See [validation evidence and limits](VALIDATION.md). No new third-party dependency was added.
